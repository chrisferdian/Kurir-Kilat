# Catatan Draft Keputusan Desain Kurir Kilat
(Bahan penyusunan NOTES.md)

## Tahap 0 & Tahap 1: Setup & Kontrak Tipe
- Pilihan Node.js 20+ dengan TypeScript & tsx: Memungkinkan eksekusi langsung file TypeScript modern (ESM) tanpa build step/bundler yang rumit, mempercepat iterasi dan memudahkan penguji menjalankan program tanpa kebingungan konfigurasi build.
- Kontrak tipe terpusat (src/shared/types.ts): Menjamin sinkronisasi 100% antara spec resmi API simulator, model internal dispatcher, dan payload dashboard.
- Toleransi enum terbuka pada CourierStatus ("idle" | "moving" | "waiting" | string): Spec API menyebut kurir bisa memiliki status lain di masa depan; string union terbuka mencegah parsing error saat ada status baru dari kota.
- Pemisahan model Order publik dan OrderView internal/dashboard: OrderView memperkaya data dengan kalkulasi risiko (ok/late/cancel) dan perkiraan ETA tanpa merusak kontrak data asli dari server kota.

## Tahap 2: Simulator Kota (P2, P3, P4)
- PRNG Mulberry32 deterministik (src/sim/rng.ts): Menggaransi pengujian berbasis seed yang identik, fundamental untuk komparasi strategi greedy vs insertion secara apel-ke-apel (ceteris paribus).
- World Engine murni terisolasi dari I/O (src/sim/world.ts): Logika tick, pergerakan sel, cuaca, dan validasi rute dibuat tanpa dependensi HTTP/Timer, menghasilkan eksekusi unit test yang instan dan bebas flakiness.
- Validasi berurutan setRoute: Mengecek status kurir (404), format stops (400), batasan stop (400), ketersediaan order (404/409), dropoff integrity (400), dan simulasi muatan kumulatif (400) sebelum memutasi rute.
- Jitter waktu masak (actual vs estimated): Menguji ketangguhan dispatcher menghadapi ketidakpastian dapur restoran tanpa membocorkan actual_ready_tick ke API publik.
- Simulasi cuaca dan kurir offline: Menyediakan skenario edge case nyata (hujan memperlambat kurir di tick ganjil, kurir offline melepaskan pesanan ASSIGNED kembali ke OPEN) untuk menguji keandalan penugasan ulang.

## Tahap 2: Simulator Server (P5)
- Server HTTP mandiri (src/sim/server.ts): Memisahkan simulator sebagai service independen di port 4000 yang dapat diakses melalui HTTP, membuktikan dispatcher bersifat black-box.
- Token Bucket Rate Limiter: Mengimplementasikan pembatasan laju 15 req/s dengan burst capacity 30 token, melempar HTTP 429 dengan header `Retry-After: 1` saat antrean penuh untuk menguji ketahanan retry pada client.
- Struktur error response seragam `{ error: { code, message } }`: Mematuhi spesifikasi kontrak resmi kota dan menguji parsing error di sisi client.

## Tahap 3: Dispatcher Core & Planner (P6, P7, P8)
- Isolasi Asumsi Dispatcher vs Realitas Kota: Dispatcher tidak membaca config simulator, melainkan berjalan dengan asumsi konservatif (`ASSUMED_PATIENCE_TICKS: 40`, dll.) untuk mencerminkan sistem produksi yang menghadapi black-box kota asli.
- Toleransi Kegagalan HTTP Client (src/dispatcher/client.ts): Mendukung retry otomatis 429 berdasar header `Retry-After`, exponential backoff pada 5xx, dan memperlakukan error 4xx dari API rute sebagai nilai pengembalian valid tanpa mematikan loop proses (tidak melempar exception fatal).
- Algoritma Insertion Heuristic & Batching Alami: Dengan mengevaluasi setiap titik sisip pickup dan dropoff pada rute kurir aktif, insertion secara alami membentuk batching pesanan yang searah tanpa membutuhkan algoritma klasterisasi terpisah.
- Blacklist Pasangan Order-Kurir (`blocked` set): Mencegah terjadinya *busy-loop* ketika API kota menolak penugasan suatu rute (misal akibat race condition kapasitas), dengan menangguhkan pasangan order-kurir tersebut selama 5 tick.

## Tahap 3: Store & Dispatcher Loop (P9, P10)
- In-Memory State dengan Batas Ring Buffer (src/dispatcher/store.ts): State disimpan langsung di memori tanpa database eksternal untuk kecepatan respons, dengan pembatasan entri log (500) dan pesanan selesai (300) untuk mencegah memory leak.
- Mekanisme Snapshot Cadangan (`data/snapshot-<runId>.json`): Menjamin pemulihan status ketika dispatcher restart di tengah run (state hydration), memulihkan event cursor dan riwayat finansial.
- Kombinasi Polling State & Event Feed Draining: `/v1/state` sebagai ground truth posisi entitas, dipadukan dengan kuras habis `/v1/events` (looping selama `has_more: true`) agar tidak ada status transisi yang luput dari perhitungan.
- Server-Sent Events (SSE) untuk Dashboard: Menggunakan SSE daripada WebSocket karena komunikasi murni satu arah (server ke dashboard), didukung reconnect bawaan browser (`retry: 2000`) dan pengiriman snapshot komprehensif instan setiap kali koneksi tersambung kembali.

## Tahap 4: Dashboard Operasional Live (P11, P12)
- Frontend Vanilla JS + SVG Murni (tanpa framework): Menghilangkan kompleksitas bundler dan dependensi, memastikan dashboard langsung jalan begitu file statis disajikan oleh Express.
- Rendering Bertingkat pada Peta SVG:
  - `layer-static`: Grid, zona, dan restoran di-cache dan hanya dirender ulang jika cuaca/peta berubah.
  - `layer-routes`: Polyline rute kurir dirender dengan pembelokan siku-siku (horizontal dulu lalu vertikal) sesuai aturan gerak kota.
  - `layer-dynamic`: Elemen kurir dan pesanan menggunakan sistem *element pooling* (Map reuse per ID), hanya memperbarui koordinat translate alih-alih me-recreate node DOM.
- Tabel Pesanan dengan Row Recycling: Memperbarui isi baris tabel per-ID alih-alih mereset innerHTML seluruh tabel, menjaga performa tetap 60 FPS dan scroll position tidak melompat.
- Sinkronisasi rAF (requestAnimationFrame): Memastikan UI hanya digambar ulang maksimal 1 kali per frame layar, bahkan jika server disetel pada kecepatan ekstrem (`TICK_MS=50`).
- Visualisasi Finansial Chart.js tanpa Animasi (`update("none")`): Menggambar pergerakan keuntungan, revenue, dan denda secara real-time tanpa lag animasi.
